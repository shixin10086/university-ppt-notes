# 伙伴Skill分工与调用顺序

本Skill是总控层，不复制另外两个Skill的文件，而是在同一任务中组合调用 `ppt-speech-writer` 与 `humanize`。只有三层各自完成职责，才算执行了完整流程。

## 一、固定分工

### `ppt-speech-writer`：PPT证据层

只使用以下能力：

- 提取文本框、表格、图表、图片、备注和OOXML文本
- 渲染全部幻灯片
- 对复杂页执行OCR或视觉检查
- 建立逐页可见元素清单
- 将最终确认稿写入PPT备注栏

不要执行它自己的语言确认、演讲时长预算、叙事弧确认、逐页显示稿、术语表、暂停标记、强调标记和Transition格式。它不能直接决定本项目的讲稿结构。

### `university-ppt-notes`：教学组织层

负责：

- 只依据PPT证据和用户当前对话指令确定内容
- 建立整讲主线、15页上下文窗口和跨案例去重
- 判断页面类型、详略、图示讲法和页间逻辑
- 按本Skill规定生成引入、备稿、收束及特殊页面模块
- 每5页送审、确认后写入累计稿
- 执行教师试讲和全稿验收

### `humanize`：表达检测层

在本Skill已经完成第一版课堂讲稿后使用检测模式，重点发现：

- PPT摘要、机械罗列、统一模板和报告式语言
- 提纲式短句、生硬连接和不自然的重复句式
- 为了口语化而出现的聊天措辞、空话或专业含义变化
- 原本自然准确、没有必要改动的句子

`humanize` 不负责确定页面重点、组织知识或完成第一次成文，也不直接接管整页重写。它返回可核对的问题线索后，由本Skill判断是否修改。任何修改都不能把教师语言变成聊天口吻，也不能改变PPT事实、格式和字数规则。

新稿和确认稿都遵循最小必要修改原则：有明确问题才改，没有问题就保留。若检测发现页面教学任务或整体信息顺序判断错误，由本Skill依据PPT证据和对应样稿重新成文，而不是让 `humanize` 自由扩写。

## 二、固定调用顺序

1. `ppt-speech-writer` 完成PPT提取、渲染与视觉证据整理。
2. 本Skill把全讲教学主线、页面组逻辑、视觉清单、详略和去重规划完整呈现给用户；用户确认前不生成首批讲稿。
3. 用户确认全讲分析后，本Skill在保留前后页关系的同时逐页独立成文；每页只读取一个对应样稿，不沿用上一页的句式生成下一页。
4. 当前5页初稿全部完成后，再读取详细写作规则核验格式、字数和专业边界。
5. `humanize` 仅用检测模式检查组合后的5页是否存在明显机械表达；本Skill核对检测结果后做最小必要修改，页面重点或整体顺序错误时才重新生成。
6. 本Skill以大学教师身份连续试讲，检查准确性、详略、连贯性、Humanize结果和格式。
7. 用户审核当前5页；确认后写入累计稿。
8. 全部页面完成并通过终检后，再使用 `ppt-speech-writer` 的备注写入能力，或使用本仓库的导出脚本完成交付。

不得让 `ppt-speech-writer` 或 `humanize` 决定讲稿语言结构。前者只提供证据，后者只发现表达问题，页面教学任务和第一次成文始终由本Skill负责。

## 三、缺失处理

- 开始任务时检查两个伙伴Skill是否已经可用。
- 缺少任一个时，准确说明缺少哪一个，并询问用户是否安装；不要声称已经使用。
- 用户明确不安装时，可以继续使用本Skill已有规则完成降级版本，但必须说明缺少的能力：没有 `ppt-speech-writer` 时无法保证完整视觉取证，没有 `humanize` 时只能由本Skill自身规则进行表达检查。
- 是否安装、从何处安装以及安装产生的外部变化，必须遵循当前环境的授权流程。
